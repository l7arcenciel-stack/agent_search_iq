ROLLOUT GUIDE — ORIGINAL TENANT

元テナントへの反映 手順書

新テナントで検証し終えた構成を、元のテナントへ追加するための差分手順。作り直しではないので、既存の凍結デモ（agent-search-hosted）を壊さないことが最優先になる。

前提: Global Administrator ではない 前提: Fabric 管理者ではない 凡例: 自分で可 管理者待ち

0この手順書の使い方

休み明け初日の動き方
  1. まず 1. 管理者への依頼 を送る。管理者権限が必要な項目はリードタイムが読めないので、何よりも先に投げる。依頼文のテンプレートをそのまま使える。
  2. 返事を待っている間に 3. 以降を進める。自分で可 のバッジが付いた手順は、管理者の完了を待たずに全部やれる。
  3. 管理者待ち の手順に行き当たったら飛ばして、次の 自分で可 に進む。
  4. 管理者から完了連絡が来たら、飛ばした手順に戻る。

結果として、管理者の返事が来る頃にはデータとレイクハウスが出来上がっている状態になる。

2【最重要】既存デモを壊さないための注意

元テナントには、いま動いている凍結デモがある。以下はどれも「気づかないうちに既存側の挙動が変わる」類の事故。

AAI Search のインデックスを既存エージェントと共有している

全社員グループの実グループ化（依頼 #3）に伴って ACL を変えて再投入すると、同じインデックスを見ている凍結中の既存エージェントの挙動も一緒に変わる。何も触っていないはずの既存デモで、突然「閲覧できません」が出るようになる。

→ 新エージェント用に別名のインデックスを作る。AZURE_SEARCH_INDEX_NAME を新エージェントの azd 環境だけで変える。既存エージェントの azd 環境には一切触らない。

B既存の OBO 用アプリ登録を変更しない

「権限を足すだけ」でも、同意状態の変化やスコープの追加が既存デモのサインインに影響する。影響範囲が読めない。

→ 新エージェント用に別のアプリ登録を作る（依頼 #4）。既存アプリには触らない。

C既存のセマンティックモデル・ワークスペースを変更しない

既存のモデルはインポートモードで、オントロジーにデータをバインドできない。ここを Direct Lake に変換しようとすると、既存デモの Power BI 経路（query_fabric_tool）が動かなくなる。

→ レイクハウス・Direct Lake モデル・オントロジーは、すべて新しいアイテムとして作る。既存モデルはそのまま残す。

D既存エージェントを再デプロイしない

既存エージェントの agent_search_hosted/requirements.txt は >= 指定で、azure.yaml が remote_build。次に再デプロイした瞬間に未検証の最新パッケージが入る。コードを1行も変えていなくても挙動が変わりうる。

→ 既存エージェントには azd deploy を打たない。どうしても必要になったら、先にバージョンを固定してから。

Eazd の環境を取り違えると既存デモの全員が再サインインになる

既存環境に誤ってデプロイすると、既存エージェントの _OBO_CACHE（プロセス内メモリ）が消える。

→ 新エージェント用の azd 環境を分け、azd deploy の前に必ず azd env list を打つ。

Fテナントを取り違える

新テナントと元テナントの両方に az login できる状態で作業する。

→ 作業前に必ず az account show でテナントを確認する。新テナント側で使った tenant_guard の期待値を、元テナントのIDに入れ替えて使う。

az account show --query "{tenant:tenantId, sub:name, user:user.name}" -o table
azd env list

Gチャットモデルの容量（TPM）を既存デモと共有する

Foundry プロジェクトを流用すると、新エージェントは既存デモと同じモデルのデプロイ（例: gpt-4.1-mini）を使う。新テナントでは、Fabric IQ のツール定義がプロンプトに乗るぶん消費が増え、容量 1（1,000 TPM）ではすぐレート制限になった。

→ 新エージェントを動かすと、凍結中の既存デモがレート制限に巻き込まれる可能性がある。デモの時間帯が重なるなら、容量を上げる（Standard は従量課金なので固定費は増えない）か、新エージェント用に別名のモデルデプロイを作って AI_FOUNDRY_MODEL を分ける。容量変更もデプロイ作成も既存デモへの影響が読みにくいので、実施前に既存エージェントの回帰確認（§6）の準備をしておく。

4追加作業の手順（差分のみ）

新テナントで実際に行った順を基本に、既存環境と重なる部分を省いた差分だけを並べた。各手順に、新テナント手順書の該当箇所へのリンクを付けてある。

目的
既存のワークスペース・モデルに触れずに、Direct Lake の置き場所を用意する。
どこで
Fabric ポータル ワークスペース > 新規 → 新規 > レイクハウス
手順
  1. 新しいワークスペースを作り、既存の Fabric 容量に割り当てる（依頼 #7 の完了が要る）。
  2. レイクハウスを作る。OneLake セキュリティは有効にしない。
  3. ワークスペースに、テストユーザー2人（または品質チーム／全社員グループ）を必要な範囲で追加する。
確認方法
新しいワークスペースが容量に紐づいて表示され、レイクハウスが開ける。既存ワークスペースは何も変わっていない。
落とし穴
既存ワークスペースの中にレイクハウスを作ると、既存デモの管理範囲と混ざって事故のもとになる。ワークスペースごと分ける。
参考: 新テナント手順書 4-1
目的
新テナントで検証済みのテーブル定義を、そのまま元テナントに再現する。
どこで
Fabric ポータル、4-1 のレイクハウスのノートブック
手順
  1. 新テナントで使ったノートブックをそのまま持ってきて実行する。
  2. 閲覧範囲ごとに分けたテーブル（公開／品質チーム限定）をそのまま作る。
  3. 4-6 の判定結果次第だが、権限確認用の混合テーブルは元テナントでは作らなくてよい（新テナントで判定済みのはず。未判定なら作る）。
確認方法
テーブルが並び、数値列が Double で、プレビューに値が出る。
落とし穴
実データを載せる場合、新テナントの合成データとは中身が違う。列名・型の制約（snake_case / Double / 列マッピング無効 / マネージドテーブル）は実データでも必ず守る。

目的
