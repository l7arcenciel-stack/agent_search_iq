0はじめに

この手順書が何を作るためのもので、何に気をつけながら進めるか。

目的

「部署をまたいで聞けるようにしても、見せてはいけないものは見せない」ことを、権限の違う2人のユーザーが同じ質問を投げて、返ってくる内容が違うという形で見せる。そのデモ一式を、新設した自前テナントの上に作り直す。

旧テナントとの関係

旧テナントの値は一切流用しない。テナントID・アプリ登録のクライアントID・シークレット・グループID・ワークスペースID・接続ID・各種キーは、すべて新しく発行されたものに置き換わる。リポジトリ内のコードはこれらをすべて環境変数から読むようになっているので、コードを書き換える必要はなく、環境変数を入れ替えるだけでよい（例外は fabric_schema.py と azure.yaml のエージェント名。後述）。

安全上の注意：テナントが2つになる

旧テナント（既存デモが動いている）と新テナントの両方に az login できる状態になる。作業の前に必ず接続先テナントを確認すること。

az account show --query "{tenant:tenantId, sub:name, user:user.name}" -o table

可能なら、テナント誤爆ガード（tenant_guard）を仕込む。手元の PowerShell プロファイルや作業用スクリプトの先頭で、想定しているテナントIDと az account show の結果が一致しなければ即座に止める、という程度のもので十分に効く。

$expected = $env:EXPECTED_TENANT_ID   # 新テナントのIDを事前に環境変数へ
$actual   = az account show --query tenantId -o tsv
if ($actual -ne $expected) { throw "テナントが違います: $actual (期待: $expected)" }

同じことが azd にも当てはまる。azd deploy の前には必ず azd env list で選択中の環境を確認する。

API / CLI でできる部分はスクリプト化してある

Entra（グループ・ユーザー・アプリ登録と管理者同意）、Fabric のアイテム、Foundry のロールは tenant_setup/、Fabric のテーブル・モデル・オントロジー定義は fabric_notebooks/。すべて --dry-run 付きで冪等。実行順は tenant_setup/README.md。この手順書の各ステップは、それらをポータルで手作業する場合の説明も兼ねている。新テナントで実際に叩いたコマンドと結果は docs/operations_log.md。

作業を再開するときは、まず状況点検スクリプトを流す 
python fabric_notebooks/00_check_status.py

読み取りだけを行い、テナント・容量・ワークスペース・レイクハウス・セマンティックモデル・オントロジー・グループ・テストユーザーの状態と、次にやること、現在の環境変数の値を表示する。ID をファイルに持たない方針なので、値はここから拾う。

コスト節約で容量を止める運用に注意。容量が停止していると、アイテムの一覧は取れるのに中身（テーブル一覧、オントロジー定義など）だけが 404 になる。スクリプトはワークスペースが実際に載っている容量の状態を最初に確認する。F2 を止めて試用容量に付け替えることもでき、今回の構成（レイクハウス・Direct Lake モデル・オントロジー）は試用容量でも動いた（§8 #1）。付け替えても F2 は自動で止まらないので、手動で停止する。

1【最重要】エラーにならずに静かに壊れるポイント

どれも例外もエラーメッセージも出ない。「なんとなく答えが薄い」「片方だけ何も出ない」という形でしか気づけないので、先に頭に入れてから作業する。

AAI Search のインデックスは、投入時点のグループIDを文書に焼き付ける

各文書の acl_groups フィールドには、投入した瞬間のグループの Object ID (GUID) が値として入る。新テナントで品質チームのグループを作ると当然 GUID は別物になる。

→ インデックスを作り直して全文書を再投入しないと、品質チーム限定の文書は「誰が聞いても閲覧できません」になる。権限デモの片側が丸ごと死ぬ。旧インデックスの流用は不可。

同じことが全社公開の文書にも起きる。旧環境では all-employees が実グループではなく文字列スラッグのままだったため、OBO でグループを解決したユーザー（Graph は GUID しか返さない）には全社公開文書も見えなくなっていた。今回は全社員グループも実グループとして作り、ALL_EMPLOYEES_GROUP_ID に GUID を入れる。

B旧テナントのプロジェクト名がハードコードされていた箇所

今回の調整で環境変数化済みだが、再発しやすいので場所を覚えておく。リポジトリ直下で git grep -n "prjfoundry123" を流して 0 件になることを確認する。

  • azure.yaml の uses: と services.<project>.endpoint → ${AI_FOUNDRY_PROJECT_ENDPOINT} に変更済み
  • client_test_responses_session.py の Responses URL → 環境変数から組み立てるよう変更済み
  • demo_chat_iq.py のエンドポイント既定値 → IQ_AGENT_NAME 経由に変更済み
  • main.py の Agent(name=...)（組織名入り）→ AGENT_DISPLAY_NAME に変更済み

→ azure.yaml のエージェント名（YAMLのキー名）だけは環境変数にできない。元テナントへ反映するときはここを手で変える。

Cインポートモードのセマンティックモデルからはデータをバインドできない 確認済

セマンティックモデルからオントロジーを生成すると、エンティティ・プロパティ・リレーションの「定義」はインポート／Direct Lake／DirectQuery のどれからでも作れる。しかし実データのバインドは Direct Lake のみ対応で、インポートと DirectQuery は非対応。

→ 画面上はオントロジーが立派に出来上がって見えるのに、Fabric IQ に聞くと中身のある答えが返ってこない。必ずレイクハウス＋Direct Lake モデルから作る。

Dフロントがオペレーターのトークンで Foundry を呼ぶと、Fabric IQ だけオペレーター権限で動く

Foundry の Fabric IQ ツール（Toolbox）は、呼び出し元ユーザーを Foundry 側で解決する（FoundryToolbox が x-agent-foundry-call-id を転送する実装）。一方 AI Search / Power BI は OBO 登録した本人の権限で動く。

→ フロントが DefaultAzureCredential（＝手元の az login）で Foundry を呼ぶと、経路によって「誰か」がずれる。2人で見比べても Fabric IQ の部分だけ2人とも同じ結果になり、デモの主張が成立しない。demo_chat_iq.py は既定で FOUNDRY_CALL_AS=user（本人のトークン、scope https://ai.azure.com/.default）で呼ぶようになっている。この既定を変えない。

Eオントロジーは手動リフレッシュしないと上流の更新が見えない 確認済

レイクハウス側のテーブルを作り直しても、オントロジーをリフレッシュするまで古いままの内容で答える。

→ データを直したのに答えが変わらないときは、まずリフレッシュを疑う。

3Entra ID

このデモの中身そのもの。ここで作るグループIDが、後の AI Search 投入と RLS の両方に効く。

先にグループを作り切る

グループIDが確定してからでないと AI Search への文書投入（4-5）に進めない。グループ → ユーザー → アプリ登録 の順で、先にこの節を終わらせてしまうのが早い。

目的
文書の ACL と、Power BI の RLS に使う実グループを用意する。
どこで
Entra 管理センター ID > グループ > すべてのグループ > 新しいグループ
手順
  1. グループの種類「セキュリティ」で、品質チーム用のグループを作る（例: grp-quality-team）。
  2. 同じく全社員用のグループを作る（例: grp-all-employees）。スラッグ文字列ではなく実グループとして作るのが今回の変更点。
  3. それぞれのオブジェクトID（GUID）をコピーして docs/tenant_config_record.md に記録する。
  4. 全社員グループには、テストユーザー2人とも入れる。品質チームグループには片方だけ入れる。
確認方法
各グループの「メンバー」に想定どおりのユーザーが入っている。グループ概要ページの URL とプロパティにオブジェクトID が表示される。
落とし穴
動的グループにしない。メンバーシップの反映に時間差が出て、デモ直前に「なぜか片方に見えない」が起きる。割り当て済み（Assigned）にする。
Graph の GroupMember.Read.All で解決されるのはグループの GUIDであり表示名ではない。環境変数には必ず GUID を入れる。
既定で存在する「All Company」は使わない。Microsoft 365 グループ（securityEnabled=false）なので、ACL やレイクハウスの権限付与には専用のセキュリティグループを作る。
CLI で作る場合の注意：新テナントはセキュリティ既定値が有効で、Graph への非対話アクセスが AADSTS530035 でブロックされる。一度だけ az login --tenant <TENANT_ID> --scope "https://graph.microsoft.com//.default" を実行し、MFA を通してから操作する。
目的
「品質チーム所属」と「未所属」の2人で、同じ質問の結果を比べられるようにする。
どこで
Entra 管理センター ID > ユーザー > すべてのユーザー > 新しいユーザー
手順
  1. ユーザーA（品質チーム所属）とユーザーB（未所属）を作る。表示名は画面に出るので、デモで見分けがつく名前にする。
  2. 3-1 のグループに割り当てる（A: 全社員＋品質チーム／B: 全社員のみ）。
  3. 利用場所（usageLocation）を設定してから、ライセンスを割り当てる。新テナントでは Power BI（無料）＝POWER_BI_STANDARD が実質無制限にあり、これだけで Fabric へのサインインとオントロジーの閲覧ができた。Pro の要否は 2-2 の【要確認】。
  4. 初回サインインを済ませ、パスワード変更・MFA 登録を完了させておく。
確認方法
2人ともブラウザで https://app.fabric.microsoft.com にサインインでき、ライセンスエラーが出ない。
落とし穴
デモ本番当日に初回サインインをやらせない。パスワード変更と MFA 登録の画面が挟まって確実に時間を食う。セキュリティ既定値が有効なテナントでは MFA が必須なので、Authenticator を2アカウント分登録する準備も要る。
利用場所が未設定だとライセンス割り当てが失敗する（invalid usage location）。設定直後も反映待ちで失敗することがあるので、数十秒おいて再試行する。
テナントが持っている POWER_BI_STANDARD は Power BI Pro ではなく無料版。ポータル右上の「Power BI 試用版 残り◯日」は別枠の個人試用で、購読ライセンスとしては出てこない。
パスワードをメールで受け取る手段が無いので、作成時に決めた値を安全な場所に控える（リポジトリには置かない）。
目的
デモUIでのユーザーサインインと、On-Behalf-Of によるトークン交換（Graph でのグループ解決／Power BI での RLS）に使う。
どこで
Entra 管理センター ID > アプリケーション > アプリの登録 > 新規登録
手順
  1. アプリを登録する（例: app-agent-search-iq-obo）。サポートされるアカウントの種類は「この組織ディレクトリのみ」。
  2. 認証 で「パブリック クライアント フローを許可する」をはいにする（デバイスコードフローに必須）。
  3. API の公開 でスコープ access_as_user を追加する。アプリケーション ID の URI は既定の api://<CLIENT_ID> のままでよい。
  4. API のアクセス許可 に委任のアクセス許可を追加する：
    • Microsoft Graph → GroupMember.Read.All、User.Read
    • Power BI Service → Dataset.Read.All
    • Azure Machine Learning Services → user_impersonation。これが https://ai.azure.com の実体（appId 18a66f5f-dbdf-4c17-9dd7-1634712a9cbe）。デモUIの FOUNDRY_CALL_AS=user で本人のトークンを取るのに使う。「所属する組織で使用している API」タブで名前を検索する
  5. 管理者の同意を与える（自分が Global Administrator なのでその場でできる）。自分自身の access_as_user にも同意が要る（デモUIが自アプリの API のトークンを取るため）。
  6. 証明書とシークレット でクライアントシークレットを作り、値を安全な場所に保管する（画面を離れると二度と見られない）。
確認方法
アクセス許可の一覧で、追加したすべての権限の状態が「<テナント名> に付与されました」の緑チェックになっている。
実地確認としては、5-5 の後に streamlit run demo_chat_iq.py でサインインが通ること。

検証の経過：

  • オントロジーへの読み取りだけを与えた状態 → 全エンティティが 401 Unauthorized。スキーマは見えるがデータは1行も引けない（「オントロジー＋裏のソースの両方に読み取りが必要」が実証された）

つまりレイクハウスのアイテム権限は全か無かで、テーブル単位の制御は効かない。OneLake セキュリティなら行・列レベルの制御ができるが、有効にするとオントロジーのバインド対象から外れるため使えない（共有ダイアログに「OneLake セキュリティ」タブがあるので紛らわしい）。

解決策：閲覧範囲ごとにレイクハウスを分ける。エンティティのデータ問い合わせはバインド元のレイクハウス単位で個別に認可されるので、これでエンティティ単位の分離が成立する。オントロジーは1つのままでよい。

lh_public      … 全社公開のエンティティ    → 全社員グループに読み取り
lh_restricted  … 品質チーム限定のエンティティ → 品質チームグループのみに読み取り

ont_agent_search_iq

  • 【デモの核心】レイクハウス分割による権限分離が成立した。未所属ユーザーは product を引けて quality_document_restricted は 401、所属ユーザーは両方引ける。付与はグループ経由（lh_public→全社員、lh_restricted→品質チーム、オントロジー→全社員）
  • テナント設定 OntologyPreview は既定で有効だった。この新テナントでは最初から True。有効化の作業自体が不要なケースがある
  • japaneast で Ontology (preview) が作成できる。アイテムの種類の一覧に表示されることを確認（リージョンのゲートは通過）
  • Foundry の接続タイプ一覧に「Fabric IQ」は無い。あるのは「Microsoft Fabric（プレビュー）」のみ（→ #14 で継続）
  • オントロジーは付随の Lakehouse と GraphModel を自動生成する（→ 4-3 参照）
  • オントロジーの定義は API で書ける。定義ファイルの $schema に公開スキーマの URL が入っており、エンティティ型・バインド・リレーション型のいずれも取得できる（→ 4-3 参照）。当初「書けない」と判断したが、誤りだったので訂正した
  • オントロジーの型システムに Decimal が無い。valueType は String / Boolean / DateTime / Object / BigInt / Double の6つだけ。「Decimal 列は null になる」は仕様上の必然で、回避策が無いことが確定した（→ 4-1 参照）
  • DoubleType は正しく Double として扱われる。ポータルのバインド画面でも数値として認識され、null にならない
  • 自分で作ったレイクハウスにバインドできる。バインド定義の sourceTableProperties は sourceType: "LakehouseTable" ＋ 対象レイクハウスの workspaceId / itemId を持つ。オントロジー付随のレイクハウスを使う必要はない
  • バインドの保存にはエンティティ型キーの定義が必須。プロパティのマッピングだけでは保存できない（→ 4-3 参照）
  • 列名がテーブルと一致していればプロパティのマッピングは自動で埋まる。4-1 で snake_case を揃えておく効果がここに出る
  • セマンティックモデルは API（TMSL）で作成でき、Direct Lake になる。10テーブルすべて mode: directLake を確認
  • Delta テーブルのバインド前提条件は自動チェックできる。マネージドテーブル・列マッピング無効・snake_case・Decimal なし・同名プロパティの型一致を 01_create_delta_tables.py の末尾で検証している
